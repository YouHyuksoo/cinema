# 소스 데이터 파이프라인 아키텍처 설계

- 작성일: 2026-09-10
- 상태: 설계 진행 중 (계층 뼈대 확정, 중간 계층 미정)
- 관련 문서: docs/standards/scene-data-contract.md(도착지의 입력 계약), docs/specs/2026-09-10-render-common-refactor-design.md(소비자 쪽 리팩터, 병행)

## 1. 뼈대 — 3계층

```
┌─ 소스층 (데이터 원천) ──────────────────────────┐
│ 설비(EQUIPMENT) │ DB │ FEED │ SENSOR │ … 추가 가능 │
└──────────────────────┬─────────────────────────┘
                       ▼
┌─ 중간 계층 (미정 — 일단 비워둠) ─────────────────┐
│ 정제·가공·중계. 규칙이 생기면 여기에 채운다.        │
└──────────────────────┬─────────────────────────┘
                       ▼
┌─ 도착지 (정제된 데이터가 모이는 곳) ──────────────┐
│ sceneDataStore — 소스가 무엇이든 같은 형태로 모임   │
└──────────────────────┬─────────────────────────┘
                       ▼
┌─ 소비자 ────────────────────────────────────────┐
│ 연출(draw*Film) · 액션(HATCHERY 값 변경) · 헬스 표시 │
└──────────────────────────────────────────────────┘
```

## 2. 확정된 규칙

1. **소스층은 도착지를 모른다.** 소스별 어댑터가 소스 형태를 도착지가 받는 형태(장면 데이터 계약의 봉투·객체 패치)로 번역하는 것까지만 한다.
2. **도착지는 소스를 모른다.** 이미 구현된 `sceneDataStore`(replace/patch/subscribe + provenance)가 그대로 도착지다. 새로 만들지 않는다.
3. **소비자는 도착지만 본다.** 연출·액션 코드가 소스나 중간 계층을 직접 부르는 일은 없다.
4. **중간 계층은 지금 정하지 않는다.** 정제·변환 규칙이 실제로 필요해지는 시점에 이 문서에 채워 넣는다. 미리 만들지 않는다.

## 3. 현재 구조와의 대응

| 계층 | 현재 구현 | 상태 |
|---|---|---|
| 소스층 | DB(oracleSource/feedRunner), 정적 JSON(staticSceneData), AI 명령(hatcheryTargets) | 동작 중. 설비·SENSOR·MQ는 소스가 아직 없음 |
| 중간 계층 | 없음 | 비워둠 (§2-4) |
| 도착지 | sceneDataStore + sceneDataRegistry + 장면 데이터 계약 | 확정, 변경 없음 |
| 소비자 | draw*Film(연출), HATCHERY 패치(액션), 신호 감지기(헬스) | 동작 중 |

## 4. 새 소스가 들어올 때의 절차 (소스층 추가 규칙)

1. 소스의 원시 형태를 확인한다.
2. 소스별 어댑터를 하나 만든다 — 출력은 반드시 도착지의 봉투 또는 객체 패치.
3. 도착지와 소비자는 손대지 않는다. 장면이 새 데이터를 받아야 하면 계약의 등록부(registry)에만 추가한다.

## 5. 앞으로 이 문서에 채울 것

- 중간 계층: 필요가 생기면 (예: 여러 소스의 값을 합쳐야 할 때, 단위 변환이 소스마다 달라질 때)
- 소스층 항목별 상세: 설비·SENSOR·MQ가 실제로 연결될 때 각 절을 추가
- 전송 방식(폴링/푸시): 중간 계층 모양이 잡힌 뒤에 정한다

## 변경 이력

- 2026-09-10: 초안 — 5계층 상세 설계였으나, 사용자 지시로 3계층 뼈대(소스→도착지→소비) + 중간 계층 보류로 단순화. seq/QoS/전송 3단 등 세부는 중간 계층 논의 시 다시 꺼낸다.
